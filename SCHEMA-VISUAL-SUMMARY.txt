3. DATA MAPPING: Usuario → User + Membership
================================================================================

INPUT:
  Usuario { id, empresaId, email, rol (OWNER|ASISTENTE_LOCAL|PROVEEDOR|REPARTIDOR),
            estadoLegajo, activo, passwordHash, googleId, ... }

TRANSFORMATION:
  1. Create User row:
     { id: new UUID, email, nombre, passwordHash, googleId, fotoUrl }
     Link back: Usuario.userId = User.id

  2. Create Membership row:
     { id: new UUID, userId, businessId (=empresaId),
       role: Usuario.rol (DEPRECATED field),
       status: ACTIVE (if activo=true) | SUSPENDED }

  3. Create RoleGrant row:
     { id: new UUID, membershipId,
       roleTemplateId: map(Usuario.rol → RoleTemplate.id),
       status: ACTIVE }

  4. For each CapabilityDefinition in RoleTemplate:
     Create CapabilityGrant { roleGrantId, capabilityId }

CARDINALITY CHECKS:
  ✓ 1 Usuario → 1 User (per email, deduplicated)
  ✓ 1 Usuario → 1 Membership (per Empresa)
  ✓ 1 Membership → 1+ RoleGrant (MVP = 1 primary)
  ✓ 1 RoleGrant → N CapabilityGrant (per RoleTemplate content)
  ✓ All FKs cascade/restrict per policy


4. AUTHORIZATION FLOW (D-006: 4-Point Validation)
================================================================================

Request →
  │
  ├─→ [1] Authenticate User (verify identity)
  │        └─→ User row exists, token valid
  │
  ├─→ [2] Establish Business Context
  │        └─→ Client specifies businessId (header/path/query)
  │
  ├─→ [3] Validate Membership
  │        └─→ Membership exists for (userId, businessId)
  │        └─→ Membership.status = ACTIVE
  │
  ├─→ [4] Check Authorization
  │        └─→ RoleGrant exists for Membership
  │        └─→ CapabilityGrant exists for action
  │
  └─→ GRANT or DENY

CRITICAL: Token alone does NOT authorize. All 4 validations required.


5. MIGRATION PHASES
================================================================================

PHASE 0: PREPARE
  └─ Add new models (User, Profile, RoleTemplate, CapabilityDefinition,
                      RoleGrant, CapabilityGrant) — Prisma migration
  └─ Add new link columns (Usuario.userId, Cliente.userId) — nullable, non-breaking

PHASE 1: BACKFILL
  └─ Create User rows (1 per distinct email)
  └─ Create Membership rows (1:1 per Usuario)
  └─ Create RoleGrant rows (map Usuario.rol)
  └─ Create CapabilityGrant rows (inherit from RoleTemplate)
  └─ Validate: no orphans, FK integrity, email uniqueness

PHASE 2: TRANSITION (Dual-Read / Dual-Write)
  └─ Accept both `empresaId` and `businessId` in API
  └─ Create Usuario + User + Membership on new staff signup
  └─ New endpoints use Membership context
  └─ Legacy endpoints continue using Usuario (for backward compat)

PHASE 3: CUTOVER
  └─ Disable Usuario creation/updates
  └─ Enforce Membership-based auth
  └─ Invalidate legacy tokens (force re-login per OR-002-E)

PHASE 4: CLEANUP
  └─ Drop deprecated fields
  └─ Archive or delete Usuario table (optional)
  └─ Optionally rename Empresa → Business (schema rename)

7. CRITICAL RISKS & MITIGATIONS
================================================================================

RISK: Email uniqueness violation (legacy duplicates)
  → Mitigation: Normalize (lowercase), deduplicate in migration, specify criterion in spec

RISK: Orphan Membership/RoleGrant rows
  → Mitigation: FK validation script post-migration, test ON DELETE constraints

RISK: Authorization bypass (Membership not validated)
  → Mitigation: 4-point validation NON-NEGOTIABLE, test all auth paths

RISK: Cross-tenant access (User access Business2 from Business1 context)
  → Mitigation: Always validate businessId against Membership; never trust client

RISK: Stale token (old session after cutover)
  → Mitigation: Invalidate legacy tokens, force re-login per OR-002-E
