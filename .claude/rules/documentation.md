# Documentation and decision traceability rules

- Keep current behavior (AS-IS), target behavior (TO-BE), and implementation status distinct.
- Do not treat mockups, Figma frames, proposed APIs, roadmap entries, or specs as proof of implementation.
- Do not invent or silently close business decisions, state transitions, API contracts, or acceptance criteria.
- Link claims to concrete evidence where possible: repository path and symbol, test name, workflow run/job, commit SHA, or decision record.
- If referenced canonical documents are absent from the checkout or not tracked, state that limitation rather than reconstructing their contents from memory.
- Update documentation when an in-scope implementation changes observable behavior or operational procedures.
- Mark unresolved conflicts and identify the decision owner needed to resolve them.
