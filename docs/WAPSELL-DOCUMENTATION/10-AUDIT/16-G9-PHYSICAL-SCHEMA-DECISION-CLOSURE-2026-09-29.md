## 2. Accepted decisions

| # | Decision | Accepted choice |
|---|---|---|
| 1 | Physical table naming during migration | Preserve existing physical tables during additive migration; defer physical renames such as Empresa→Business until a later retirement/cleanup stage. |
| 2 | Prisma model naming | Use canonical Wapsell/English model names for the target model; use Prisma `@@map` where required to coexist with existing physical tables. |
| 3 | Membership ID | UUID primary key generated by Prisma; enforce `unique(userId,businessId)`. |
| 4 | Role ID | UUID primary key plus stable unique role `code`. |
| 5 | Permission strategy | Reuse the existing permission catalog as the target Permission identity/semantics where compatible; do not create a parallel permission catalog. Keep UsuarioPermiso during transition. |
| 6 | Normalized User email | Add an explicit normalized User email representation based on `lower(trim(email))` and enforce global uniqueness on that normalized value. |
| 7 | Membership active state | `User.active` and `Membership.active` are independent. User.active is global identity state; Membership.active controls access to a Business. |
| 8 | Customer→User | Nullable Customer.userId FK to User. Customer remains Business-scoped and this link does not create Membership. |
| 9 | Delete/update actions | Conservative referential integrity. Identity/tenant references are restrictive by default; optional Customer→User linkage may use SET NULL. No cascade deletion of Business→Membership/User. |
| 10 | Legacy retirement | Add → backfill → validate → dual/runtime compatibility → cutover → validate → retire legacy. Legacy fields are not removed before consumers and parity are verified. |

## 3. Target physical intent

The target relationship is:

`User → Membership ← Business`

with:

`Membership → Role → RolePermission → Permission`

Business identity is preserved through:

`Business.id == Empresa.id`

User identity is preserved through:

`User.id == Usuario.id`

The migration must NOT reduce the transformation to `Usuario.empresaId → businessId`.

## 4. Email identity invariant

The selected identity rule is:

> same normalized email = same person.

Normalization:

`lower(trim(email))`

The implementation must enforce global uniqueness on the normalized User representation before identity cutover.

Customer email remains Business-scoped. Customer email normalization is used only for deterministic Customer→User linkage.

## 5. Authorization invariant

After cutover, authorization is contextual:

`Authenticated User → Business Context → Membership → Role/Permission → Business Rule → Resource → Action`

Legacy `Usuario.rol` and `UsuarioPermiso` are compatibility sources only during migration and cannot remain the canonical authorization source after cutover.

## 6. Explicit non-decisions

- final legacy-drop migration.

These are not additional Owner business decisions unless implementation reveals a behavior or architecture conflict.
